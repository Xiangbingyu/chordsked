# ChordSked 单体后端向微服务架构迁移说明

## 1. 文档目标

本文档回答 3 个问题：

1. `chordsked-common-core`、`chordsked-common-web`、`chordsked-gateway`、`chordsked-notification` 分别适合放什么代码。
2. 现有单体后端 `e:\Github\chordsked\backend\` 中的代码应该如何迁移到 `e:\Github\chordsked\backend-cloud\`。
3. 迁移时哪些代码应该直接搬，哪些代码应该重构后再搬。

本文基于当前规划：

- 统一认证服务：`chordsked-auth`
- 教务端服务：`chordsked-admin`
- 教师端服务：`chordsked-teacher`
- 学员端服务：`chordsked-student`
- 网关服务：`chordsked-gateway`
- 通知服务：`chordsked-notification`
- 公共模块：`chordsked-common-*`

---

## 2. 总体迁移原则

### 2.1 按职责迁移，不按原包名整包复制

单体项目中的包结构是按技术分层组织的，但微服务项目需要按职责边界重新分配。

因此迁移原则不是：

```text
把 backend/common 全部复制到 common
把 backend/security 全部复制到 security
把 backend/service 全部复制到某个服务
```

而应该是：

```text
先判断代码解决的是什么问题
再判断这个问题属于公共能力、接入层能力、认证能力还是某个业务服务能力
最后决定归属模块
```

### 2.2 先抽稳定能力，再拆业务能力

建议迁移顺序：

1. 先抽 `common-core`
2. 再抽 `common-web`
3. 再抽 `common-security`、`common-redis`、`common-kafka`
4. 然后迁移 `gateway`
5. 然后迁移 `auth`
6. 然后迁移 `admin`
7. 最后迁移 `teacher`、`student`、`notification`

### 2.3 共享数据库，按表归属管理

当前阶段建议仍然使用一个 MySQL 数据库，但明确表归属：

- `admin-service` 负责教务端用户、角色、权限、校区
- `teacher-service` 负责教师用户相关表
- `student-service` 负责学员用户相关表
- `notification-service` 负责登录日志、审计日志、操作日志

跨服务需要共享数据时：

- 优先通过内部 API 暴露
- 不要把别人的 DAO、Mapper、Entity 直接复制进自己服务

## 3. 各模块职责边界

## 3.1 `chordsked-common-core`

### 适合放的代码

`common-core` 适合放所有服务都依赖、且不依赖 Web 容器的基础能力：

- 统一返回体
- 基础异常定义
- 通用错误码
- 通用枚举
- 纯工具类
- 通用常量
- 服务间共享的轻量 DTO

推荐放入的内容：

- `ApiResponse`
- `PageResult`
- `BusinessException`
- `ErrorCode`
- `AccountUserType`
- 日期、JSON、字符串、脱敏、规范化等纯工具类

### 不适合放的代码

以下内容不要放到 `common-core`：

- `Controller`
- `Service`
- `DAO`
- `Mapper`
- Spring MVC 拦截器
- Servlet Filter
- Spring Security 配置
- MyBatis XML
- 具体业务实体

### 判断标准

如果一段代码满足以下条件，通常可以进入 `common-core`：

1. 不依赖具体业务表
2. 不依赖某个微服务的业务上下文
3. 不依赖 Servlet、WebFlux、MyBatis
4. 至少两个以上服务需要使用

---

## 3.2 `chordsked-common-web`

### 适合放的代码

`common-web` 适合放传统业务服务共享的 Web 层通用能力，主要服务对象是：

- `auth-service`
- `admin-service`
- `teacher-service`
- `student-service`
- `notification-service`

推荐放入的内容：

- 全局异常处理器
- 通用 Jackson 配置
- 请求链路追踪
- 幂等组件
- 审计注解和审计切面
- 统一参数绑定增强
- 通用 Web MVC 配置

建议内容：

- `GlobalExceptionHandler`
- `TraceIdFilter` 或 `TraceIdInterceptor`
- `Idempotent` 注解、拦截器、配置
- `AuditLog` 注解、切面、提取器接口
- 通用返回包装约定

### 不适合放的代码

以下内容不要放到 `common-web`：

- 业务 Controller
- 业务 Service
- DAO 和 Mapper
- 网关专用过滤器
- WebFlux 专用组件
- 某个服务独有的审计提取器实现

### 重要边界

`common-web` 主要面向 Spring MVC 风格的业务服务，不建议把 `gateway` 的代码放进去。

原因：

- `gateway` 基于 Spring Cloud Gateway，底层是 WebFlux
- `common-web` 通常是 Servlet/MVC 体系
- 两者的过滤器、异常处理、请求上下文模型不同

因此：

- MVC 共享能力进 `common-web`
- Gateway 的过滤器和异常处理留在 `chordsked-gateway`

---

## 3.3 `chordsked-gateway`

### 适合放的代码

`gateway` 是接入层，不是业务层。它只负责“接入控制”，不负责业务处理。

推荐放入的内容：

- 路由配置
- CORS 配置
- 白名单配置
- Token 解析与基础鉴权
- 全局请求头透传
- TraceId 透传
- 限流、黑名单、灰度、降级等接入层规则
- 网关统一异常返回

建议内容：

- `RouteConfig`
- `CorsConfig`
- `AuthGlobalFilter`
- `TraceGlobalFilter`
- `GatewayExceptionHandler`
- 白名单路径配置

### 不适合放的代码

以下内容不要放到 `gateway`：

- 业务 Controller
- 业务 Service
- 业务 DAO
- Mapper XML
- 业务 Entity
- 排课、角色、学员、教师等业务逻辑
- 登录状态写库

### 特别说明

`gateway` 可以做：

- 校验请求是否携带 Token
- 解析 Token 基本信息
- 将用户标识透传给下游服务

`gateway` 不应该做：

- 查询数据库获取完整业务对象
- 承担完整登录逻辑
- 承担权限模型装配
- 写入业务日志表

也就是说，`gateway` 负责“挡门”和“转发”，不负责“办业务”。

---

## 3.4 `chordsked-notification`

### 适合放的代码

`notification` 是异步消费和通知服务，不是主业务服务。

推荐放入的内容：

- Kafka 消费者
- 登录日志落库
- 审计日志落库
- 操作日志落库
- 短信发送
- 邮件发送
- 站内消息发送
- 失败重试
- 死信处理

建议内容：

- `LoginLogConsumer`
- `AuditLogConsumer`
- `SmsConsumer`
- `MailConsumer`
- `LoginLogService`
- `AuditLogPersistService`
- `SmsService`

### 不适合放的代码

以下内容不要放到 `notification`：

- 登录逻辑
- Token 签发
- 角色权限判断
- 教师、学员、教务用户核心业务
- 网关路由逻辑

### 设计原则

`notification` 应该尽量做到：

- 只消费消息，不反向侵入业务主流程
- 消费失败可重试
- 处理逻辑幂等
- 适合写日志和发通知这类异步场景

## 4. 旧单体项目到新微服务项目的迁移分配

## 4.1 单体项目现状概览

当前单体项目主要目录如下：

```text
backend/src/main/java/com/chordsked/backend/
├── audit/
├── cache/
├── common/
├── config/
├── controller/
├── dao/
├── datascope/
├── exception/
├── idempotent/
├── model/
├── security/
├── service/
└── utils/
```

这些目录在微服务中不会原样保留，而会分发到 `common`、`gateway`、`auth`、`admin`、`teacher`、`student`、`notification` 中。

---

## 4.2 包级迁移映射

### 4.2.1 `common/` -> `chordsked-common-core`

原路径：

- `backend/common/ApiResponse.java`
- `backend/common/PageResult.java`

目标：

- `backend-cloud/chordsked-common/chordsked-common-core`

说明：

- 这部分是典型公共基础模型，适合直接抽取
- 包名建议统一重构为 `com.chordsked.common.core.*`

---

### 4.2.2 `exception/` -> `common-core` + `common-web` + 服务内

原路径：

- `backend/exception/BusinessException.java`
- `backend/exception/ErrorCode.java`
- `backend/exception/GlobalExceptionHandler.java`
- `backend/exception/SecurityExceptionHandler.java`

建议分配：

- `BusinessException` -> `chordsked-common-core`
- `ErrorCode` -> `chordsked-common-core`
- `GlobalExceptionHandler` -> `chordsked-common-web`
- `SecurityExceptionHandler` -> 不建议直接抽公共，按服务分别实现

说明：

- 基础异常和错误码是核心能力
- 全局异常处理是 Web 层公共能力
- 安全异常处理和认证入口通常与服务框架相关，`auth`、`gateway`、`admin` 可各自保留

---

### 4.2.3 `audit/` -> `common-web` + `notification` + `admin`

原路径：

- `backend/audit/annotation/*`
- `backend/audit/aspect/*`
- `backend/audit/config/*`
- `backend/audit/model/*`
- `backend/audit/provider/*`

建议分配：

- `annotation/` -> `chordsked-common-web`
- `aspect/` -> `chordsked-common-web`
- `model/` 中通用上下文对象 -> `chordsked-common-web`
- `provider/support/` 中抽象提取器接口 -> `chordsked-common-web`
- `provider/internaluser/*` -> `chordsked-admin`
- `provider/role/*` -> `chordsked-admin`
- 审计日志最终落库逻辑 -> `chordsked-notification`

说明：

- 审计“切面能力”是公共的
- 审计“提取什么字段”通常是业务相关的，应留在业务服务
- 审计“最终写入日志表”适合异步化，放到 `notification`

---

### 4.2.4 `idempotent/` -> `chordsked-common-web`

原路径：

- `backend/idempotent/annotation/*`
- `backend/idempotent/config/*`
- `backend/idempotent/filter/*`
- `backend/idempotent/interceptor/*`

目标：

- `backend-cloud/chordsked-common/chordsked-common-web`

说明：

- 幂等是典型公共 Web 能力
- 业务服务按需启用即可

---

### 4.2.5 `cache/` -> `common-redis` + `auth`

原路径：

- `backend/cache/auth/*`
- `backend/cache/security/*`

建议分配：

- 通用 Redis 操作能力 -> `chordsked-common-redis`
- 认证态缓存、登录态缓存、权限缓存 -> `chordsked-auth`

说明：

- `RedisTemplate` 封装、Key 生成器、序列化配置属于公共能力
- “登录快照”“Token 状态”“安全缓存”属于认证域能力，应该进 `auth-service`

---

### 4.2.6 `security/` -> `common-security` + `auth` + 各业务服务 + `gateway`

原路径：

- `backend/security/account/*`
- `backend/security/config/SecurityConfig.java`
- `backend/security/jwt/JwtAuthenticationFilter.java`
- `backend/utils/jwt/JwtTokenUtils.java`
- `backend/config/properties/JwtProperties.java`

建议分配：

- `JwtTokenUtils` -> `chordsked-common-security`
- `JwtProperties` -> `chordsked-common-security`
- `security/account/provider/*` -> `chordsked-auth`
- `MultiAccountUserDetailsService` -> `chordsked-auth`
- `SecurityConfig` -> `auth`、`admin`、`teacher`、`student` 各自实现
- `JwtAuthenticationFilter` 不建议直接复用原 Servlet 版本

特别说明：

- `gateway` 需要的是响应式 `GlobalFilter`
- 单体中的 `JwtAuthenticationFilter` 是 Servlet Filter
- 因此 Token 工具可以共用，但过滤器要分别实现

---

### 4.2.7 `config/` -> 按配置归属分拆

原路径：

- `backend/config/RequestIdFilter.java`
- `backend/config/properties/*`

建议分配：

- `RequestIdFilter` -> `chordsked-common-web`
- `RedisProperties` -> `chordsked-common-redis` 或各服务配置绑定类
- `JwtProperties` -> `chordsked-common-security`
- `AuthLoginProperties` -> `chordsked-auth`
- `DataScopeProperties` -> `chordsked-admin`
- `InternalUserProperties` -> `chordsked-admin`
- `RoleProperties` -> `chordsked-admin`
- `AuditAsyncProperties` -> `chordsked-common-web` 或 `chordsked-notification`
- `AppProperties` -> 不建议保留统一大配置类，拆分到具体服务

---

### 4.2.8 `datascope/` -> `chordsked-admin`

原路径：

- `backend/datascope/*`

目标：

- `backend-cloud/chordsked-admin`

说明：

- 数据权限明显是教务端 RBAC 范畴
- 教师端和学员端当前不需要这个复杂度
- 不应该抽到 common

---

### 4.2.9 `controller/` -> 分发到 `auth`、`admin`、`student`

原路径：

- `AuthController.java` -> `chordsked-auth`
- `InternalUserController.java` -> `chordsked-admin`
- `RoleController.java` -> `chordsked-admin`
- `PermissionController.java` -> `chordsked-admin`
- `StudentController.java` -> `chordsked-student`

说明：

- Controller 是最典型的业务边界入口，应按业务域迁移
- 不应抽到 common

---

### 4.2.10 `service/` -> 按业务域拆分

原路径建议分配：

- `service/auth/*` -> `chordsked-auth`
- `service/verification/*` -> `chordsked-auth`
- `service/internaluser/*` -> `chordsked-admin`
- `service/role/*` -> `chordsked-admin`
- `service/permission/*` -> `chordsked-admin`
- `service/security/AuthorityCodeService*` -> `chordsked-admin`
- `service/student/*` -> `chordsked-student`
- `service/audit/*` -> 发送端逻辑拆到 `common-web`，持久化逻辑进 `notification`

说明：

- `AuthorityCodeService` 依赖角色和权限模型，更适合在 `admin-service`
- `auth-service` 不直接拥有 RBAC 数据，而是通过内部接口查询

---

### 4.2.11 `dao/` 和 `mapper/` -> 按表归属拆分

原路径建议分配：

- `InternalUserDao`、`RoleDao`、`PermissionDao`、`RolePermissionDao`、`UserRoleDao`、`UserCampusDao`、`CampusDao` -> `chordsked-admin`
- `TeacherUserDao` -> `chordsked-teacher`
- `StudentUserDao` -> `chordsked-student`
- `AuditLogDao` -> `chordsked-notification`

对应 XML：

- `resources/mapper/internal/*` -> `chordsked-admin`
- `resources/mapper/role/*` -> `chordsked-admin`
- `resources/mapper/permission/*` -> `chordsked-admin`
- `resources/mapper/user/*` 中教务角色关联相关 -> `chordsked-admin`
- `resources/mapper/campus/*` -> `chordsked-admin`
- `resources/mapper/teacher/*` -> `chordsked-teacher`
- `resources/mapper/student/*` -> `chordsked-student`
- `resources/mapper/audit/*` -> `chordsked-notification`

说明：

- Mapper 和 DAO 跟数据表强绑定，必须按表归属划分
- 不允许一个服务直接带着另一个服务的 Mapper 运行

---

### 4.2.12 `model/entity/` -> 按实体所属业务拆分

建议分配：

- `InternalUserEntity`、`RoleEntity`、`PermissionEntity`、`RolePermissionEntity`、`UserRoleEntity`、`UserCampusEntity`、`CampusEntity`、`DataScopeEntity` -> `chordsked-admin`
- `TeacherUserEntity` -> `chordsked-teacher`
- `StudentUserEntity` -> `chordsked-student`
- `AuditLogEntity`、`LoginLogEntity` -> `chordsked-notification`

说明：

- Entity 是数据库模型，不建议放入 common
- 共享时应使用 DTO，不应共享 Entity

---

### 4.2.13 `model/dto/` 和 `model/vo/` -> 按接口归属拆分

建议分配：

- `dto/auth/*`、`vo/auth/*` -> `chordsked-auth`
- `dto/internaluser/*`、`vo/internaluser/*` -> `chordsked-admin`
- `dto/role/*`、`vo/role/*` -> `chordsked-admin`
- `vo/permission/*` -> `chordsked-admin`
- `dto/student/*`、`vo/student/*` -> `chordsked-student`
- 服务间调用共享的简化 DTO，可以后续抽到 `common-core`

说明：

- DTO 和 VO 先按服务内聚合
- 只有真正跨服务共享的契约模型，才抽成公共 DTO

---

### 4.2.14 `model/enums/` -> 通用枚举与业务枚举拆分

建议分配：

- `AccountUserType` -> `chordsked-common-core`
- `AuditLogActionType`、`AuditLogModule`、`AuditLogStatus` -> `common-web` 或 `notification`
- `CampusStatus`、`InternalUserStatus`、`RoleStatus`、`PermissionStatus`、`DataScopeRangeType`、`DataScopeTargetType`、`UserDataScopeType` -> `chordsked-admin`
- `StudentUserStatus` -> `chordsked-student`
- `TeacherUserStatus`、`TeacherUserLevelType` -> `chordsked-teacher`
- `LoginLogUserType`、`LoginLogResult` -> `chordsked-notification` 或共享消息模型
- `AuthLoginMethod` -> `chordsked-auth`

说明：

- 枚举不要因为“看起来很小”就全部塞进 common
- 只有跨服务复用的枚举才进 common

---

### 4.2.15 `utils/` -> `common-core` + `common-security` + 服务内

建议分配：

- `utils/normalize/*` -> `chordsked-common-core`
- `utils/jwt/JwtTokenUtils.java` -> `chordsked-common-security`
- `utils/security/SecurityPrincipalUtils.java` -> `chordsked-common-security`
- `utils/tree/PermissionTreeBuilder.java` -> `chordsked-admin`
- `utils/audit/AuditLogRequestUtils.java` -> `chordsked-common-web`
- `utils/cookie/CookieUtils.java` -> `chordsked-auth`

说明：

- 工具类也要按领域归属，不要无脑全部放 common-core

---

## 4.3 资源文件迁移映射

### 配置文件

原路径：

- `backend/src/main/resources/application.yml`
- `backend/src/main/resources/common/application-common.yml`
- `backend/src/main/resources/env/dev|test|prerelease|online/*`

迁移建议：

- 各服务保留自己的 `application.yml`
- 服务公共配置沉淀到 Nacos 配置中心
- 本地默认配置仍保留在各服务 `src/main/resources/application.yml`

建议规则：

- `gateway` 配网关路由、Nacos、Redis、鉴权白名单
- `auth` 配认证、Redis、JWT、Kafka
- `admin` 配数据库、RBAC、数据权限、Kafka
- `teacher` 配数据库、业务配置、Kafka
- `student` 配数据库、业务配置、Kafka
- `notification` 配 Kafka Consumer、日志落库、短信渠道

### SQL 和 Mapper

原路径：

- `resources/db/mysql/schema.sql`
- `resources/db/h2/schema.sql`
- `resources/mapper/**`

迁移建议：

- 初期仍保留一份统一 `schema.sql`
- 但在文档中明确各表归属
- 长期再按服务拆分 DDL 文件

建议目录：

```text
backend-cloud/
└── deploy/
    └── db/
        ├── mysql/
        │   ├── schema.sql
        │   ├── admin.sql
        │   ├── teacher.sql
        │   ├── student.sql
        │   └── notification.sql
        └── h2/
```

## 6. 最推荐的迁移落地顺序

### 第一步：先把公共模块补齐

先完成以下模块：

- `chordsked-common-core`
- `chordsked-common-web`
- `chordsked-common-security`
- `chordsked-common-redis`
- `chordsked-common-kafka`

其中优先级最高的是：

1. `common-core`
2. `common-web`
3. `common-security`

### 第二步：迁移认证链路

先迁移：

- `AuthController`
- `service/auth/*`
- `service/verification/*`
- `cache/auth/*`
- `cache/security/*`
- `security/account/*`

目标是先让 `auth-service` 独立可运行。

### 第三步：迁移教务端核心能力

迁移：

- InternalUser
- Role
- Permission
- Campus
- DataScope

目标是让 `admin-service` 成为教务核心服务。

### 第四步：迁移 gateway

不要把单体的 MVC 安全过滤器直接搬进去，而是：

- 复用 JWT 工具
- 重写响应式 `GlobalFilter`
- 完成路由、白名单、异常处理

### 第五步：迁移 notification

优先迁移：

- 登录日志消费
- 审计日志消费
- 落库能力

这样可以让日志类能力从主业务请求中剥离。

### 第六步：迁移 teacher 和 student

这两个服务当前复杂度低于 `admin-service`，建议后置处理。

---

## 7. 最终结论

### 模块边界结论

- `common-core` 放纯基础能力，不放业务、不放 Web、不放 DAO
- `common-web` 放 MVC 共享能力，不放 Gateway 响应式组件
- `gateway` 只做接入控制，不做业务处理
- `notification` 只做异步消费、日志持久化和通知发送

### 单体迁移结论

- 单体中的 `common`、`exception`、`idempotent` 最适合最先抽离
- 单体中的 `security/account`、`cache/auth`、`service/auth` 应优先迁移到 `auth-service`
- 单体中的 `internaluser`、`role`、`permission`、`datascope` 应整体迁移到 `admin-service`
- 单体中的教师、学员数据访问层按实体归属分别迁移到 `teacher-service` 和 `student-service`
- 单体中的审计和日志最终落库能力，应迁移到 `notification-service`

### 实施建议

不要追求一次性把单体所有代码全部搬完，应该按下面节奏逐步落地：

1. 抽公共能力
2. 跑通 gateway + auth
3. 跑通 admin
4. 接入 Kafka 和 notification
5. 再拆 teacher/student

这样风险最小，也最符合你当前 `backend-cloud` 的初始化状态。
