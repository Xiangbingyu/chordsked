# 代码评审检查清单（基于《打回历史》整理）

## 1. 接口与分层

- API 路径必须按端区分，并固定为统一格式：`{client}/api/{version}/{method}`。
- 三端路径约定：学生端 `students/api/{version}/{method}`，教师端 `teachers/api/{version}/{method}`，教务端 `admin/api/{version}/{method}`。
- Controller 层必须做入参校验（必填、长度、格式、分页参数边界）。
- Controller 查询/编辑入口优先保持统一结构：Controller 接收路径/查询/Body 参数后，组装对应 `Request DTO` 再调用 Service，不在 Controller 直接拼业务结果。
- Service 层必须做参数校验，空对象、非法值要提前返回或抛业务异常。
- 查询链路优先使用 `Request DTO + ResultVO` 结构；即使详情接口当前只有单个 `id`/`roleId` 参数，也可保留独立 `Request DTO` 以保持结构一致。
- DAO 层同样要做参数校验，禁止把非法参数直接透传到 SQL。
- Service 不直接依赖 Mapper，必须通过 DAO Interface 访问数据层。
- 每张表建议只对应一个 Mapper，避免多 Mapper 操作同表导致遗漏维护。
- Service 涉及业务一致性时必须加事务。
- Service 尽量不引入 Servlet 等 Controller 特有对象。
- 列表查询、详情查询、创建、编辑等主链路应优先拆分为独立 Service，避免把“分页查询”“详情聚合”“写操作”混在同一个 Service 中。

## 2. 安全与鉴权

- 角色与权限命名必须统一，不允许混用 `ROLE_ADMIN` 和 `ADMIN` 两套体系。
- 权限码建议带端前缀（如 `admin:user:view` / `teacher:...` / `student:...`）。
- 权限树变动频繁时，直接在代码内维护（如 enum/常量树），避免先落库导致频繁改表与迁移。
- Security 配置应默认拒绝（`denyAll`），只放行显式声明的路径。
- 公共 API 若不做细粒度权限校验，也必须经过基础角色校验。
- JWT 解析必须做过期校验、格式校验、签名校验。
- 禁止吞异常：JWT 相关异常要分级记录日志（debug/warn/error）。
- 登录失败需要审计日志，但绝不能记录明文密码。
- Token 存储优先 httpOnly Cookie，避免仅依赖 localStorage。
- 建议支持 refresh token 续期机制。

## 3. 用户模型与状态字段

- UserDetails 相关状态方法要完整实现：账号是否过期、是否锁定、凭证是否过期、是否启用。
- 用户类型、状态、等级等业务字段优先使用 enum，不要直接散落 Integer/String。
- 枚举要定义稳定 code，避免依赖 `name()` 字符串比较。
- VO 层可表达枚举语义时优先使用 enum，而不是裸数字。

## 4. 数据库与缓存设计

- 时间字段统一毫秒级 BIGINT（如 created_at、updated_at、locked_until），避免 DATETIME 混用。
- 业务删除态可并入 status 管理时，不再额外维护 is_deleted。
- 表字段类型能用 TINYINT 枚举的尽量不用 VARCHAR 枚举字面量。
- 字段要补齐 COMMENT，提升可维护性。
- 尽量减少 DB 默认值，把默认逻辑放到代码层可控处理。
- 登录失败次数、锁定时间、短信验证码等短期状态优先放 Redis，不落 MySQL。
- 图片资源（如 avatar）统一走对象存储（OSS），数据库只保留引用地址。
- 若权限树变化频繁，优先考虑代码枚举树维护而非数据库表维护。

## 5. 依赖注入与配置

- 注入优先使用 `@Resource(name = "...")` 明确 Bean，避免歧义注入。
- `@Bean` 定义建议明确命名，保证引用稳定、排查方便。
- 关注 Bean 初始化顺序，避免运行时空依赖判断堆叠。
- 测试环境配置（如 test mysql）不要随意变更，避免影响测试服一致性。
- 业务时长参数（如锁定分钟数、失败阈值、缓存 TTL）必须抽到配置项，不允许硬编码在业务逻辑中。
- 业务规则型常量（如系统预置角色编码、白名单、开关阈值、批量限制等）同样不应硬编码在 Service/Controller 中，优先抽到 `backend/src/main/java/com/chordsked/backend/config/properties/` 下的 `@ConfigurationProperties` 类中统一管理。
- 若同一职责域存在多种实现并需要按用户类型、数据范围、登录方式等维度动态分发，优先采用 `接口 + Provider/Strategy 实现 + 路由服务/路由表` 结构，由入口在启动期收集 `List<Provider/Strategy>` 并建立 `枚举/类型 -> 实现` 映射，不要在入口类中直接注入多个具体实现再手写 `if/else` 分发。
- 上述路由型结构在启动期必须校验重复实现并直接失败，避免运行期出现歧义路由。

## 6. 文档与可维护性

- 关键安全配置（例如禁用 CSRF）必须写清楚原因，便于后期排查。
- Swagger 注解建议补齐 summary + description，接口语义清晰。
- 代码格式保持一致，避免单行 Getter/Setter 等不统一写法。
- 方法命名统一采用 `动词 + 领域对象 [+ 场景/结果]` 的 `lowerCamelCase` 结构，禁止同一职责域内混用近义前缀（如 `addCookie` / `writeCookie`、`getSnapshot` / `loadSnapshot`）。
- 查询类方法统一使用 `get...`（直接读取现有数据）或 `load...`（包含装载、回源、聚合逻辑）；构建类方法统一使用 `build...`；布尔判断统一使用 `is...` / `has...` / `can...`。
- 有副作用的方法必须使用语义明确的动作前缀：写响应或输出内容使用 `write...`，清理状态使用 `clear...`，缓存写入使用 `cache...`，记录事件使用 `record...` / `audit...`，状态标记使用 `mark...`，避免使用 `add...`、`do...`、`handle...` 等泛化命名。
- Controller / Service 对外业务入口优先使用业务语义动词（如 `login`、`logout`、`refreshToken`），不要把技术细节塞进入口方法名。
- DTO / VO 命名优先贴合主链路语义，统一采用 `主服务名 + Request / ResultVO` 风格，避免同一职责域内并存多套近义命名。
- 常见异常捕获点必须记录日志，保证线上可观测性。
- 若多个 Controller 需要构造 `AuditLogRecordRequest`，必须复用统一工具类或公共构造函数（如 `utils` 下的公共方法），禁止在各 Controller 中重复拼接 `HttpServletRequest`、`SecurityContextHolder`、`ChordSkedUserDetails` 解析逻辑。
- 对用户状态校验、数据权限策略、登录方式装载等可扩展职责，优先复用统一接口路由模式，保持实现层只关注单一职责，入口层只负责路由与兜底校验。
- 数据权限链路若使用 `@DataScope`，对应 Mapper 方法禁止同名重载，避免注解解析歧义。
- 带 `@DataScope` 的 SQL 必须显式预留固定占位符 `/*DATA_SCOPE*/`，不允许依赖拦截器猜测 `WHERE` / `ORDER BY` / `LIMIT` 位置。
- `@DataScope` 上声明的 `tableAlias`、`scopeField` 必须和 SQL 主表别名及实际隔离字段严格一致。

## 7. 测试与验证

- 关键代码块必须有对应测试，不允许只改代码不补测试或只依赖人工点点点验证。
- 测试要覆盖正常路径、边界值、空值/非法值、异常分支、缓存命中与未命中等关键场景。
- 测试校验应以返回结果、状态变化、异常信息、缓存/数据库副作用是否正确为准，不能只看能否编译通过。
- 对缓存、鉴权、状态流转类逻辑，优先补充断言明确的单元测试或集成测试，避免只做烟雾测试。
- 数据权限拦截链路至少覆盖：占位符正常替换、占位符缺失报错、不同数据范围策略、无认证用户、`dataScopeType` 缺失、`@DataScope` 重载方法禁用等场景。
- 若链路同时依赖数据库、Redis、安全过滤器、UserDetails 装载与数据权限拦截，除单元测试外还必须补一组“正式基础设施集成测试”：数据库使用真实 H2 初始化脚本，缓存使用可连接的真实 Redis 实例，不允许整条链路只用 Mock 替代。
- 上述正式基础设施集成测试应至少覆盖：冷缓存回源数据库并回填 Redis、热缓存直接命中 Redis、请求经 JWT 过滤器进入后能够触发真实 `DataScopeInterceptor` 并得到正确查询结果。

## 8. 每次提交前必查（快速清单）

- 路由前缀是否按端统一？权限是否隔离？
- 是否严格使用三端固定路由规范（students / teachers / admin）？
- Controller/Service/DAO 三层是否都做了参数校验？
- 是否出现 Service 直连 Mapper？
- 鉴权策略是否“默认拒绝 + 显式放行”？
- 权限树是否按“高频变更走代码维护”的原则实现？
- JWT 异常是否有分类日志与过期校验？
- 是否存在明文敏感信息日志？
- 业务状态字段是否已 enum 化并使用 code？
- 时间字段是否统一为毫秒级 Long / BIGINT？
- 短期状态是否错误落库（可迁移 Redis）？
- 注入是否都指定了明确 Bean 名称？
- 是否仍存在业务参数硬编码（阈值、时长、TTL）？
- 业务规则常量是否仍被硬编码在 Service/Controller 中？是否已优先收敛到 `config/properties` 配置项？
- 若存在多实现动态分发，是否采用统一接口 + 路由表结构，并在启动期校验重复实现？
- 表结构字段是否补齐 COMMENT，是否引入不必要 DEFAULT？
- 本次改动是否补齐必要注释与接口文档说明？
- 是否为每个关键代码块补齐了可通过的测试，并覆盖正常、边界、异常场景且验证结果正确而非仅编译通过？
- 若涉及审计日志请求构造，是否统一复用公共 `AuditLogRecordRequest` 构造工具，而不是在多个 Controller 重复实现？
- 若接入 `@DataScope`，Mapper 是否禁止同名重载？SQL 是否已显式包含 `/*DATA_SCOPE*/` 占位符？
- 若改动数据权限链路，是否补齐了占位符替换、缺失占位符报错、范围策略和异常分支测试？
- 若改动安全缓存 + 数据权限 + JWT 鉴权联动链路，是否补齐“真实 H2 + 真实 Redis”的正式基础设施集成测试？
