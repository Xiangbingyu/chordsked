# 权限树改造方案 1

## 1. 目标

本方案用于支持 `org-tree` 页面的一期后端改造，核心目标如下：

1. 支持以组织树形式维护组织结构，层级为 `CAMPUS -> DEPT -> GROUP`。
2. 支持为教务端账号绑定组织节点，并以绑定结果决定数据可视范围。
3. 将数据权限范围统一收敛为 `ALL`、`ASSIGNED`、`SELF` 三种模式。
4. `sys_user_campus` 不再参与数据权限过滤，组织权限统一由新表代理。
5. 校区信息仅作为用户基础资料保留，类似姓名、手机号等属性，不再作为权限过滤依据。

## 2. 一期范围

一期只解决以下问题：

1. 组织树结构建模。
2. 组织树节点的增删改查。
3. 教务端账号与组织节点的绑定关系维护。
4. 数据权限过滤链路切换到组织授权模型。
5. 用户主归属组织和基础校区信息同步更新。
6. 缓存失效与登录态数据同步。

一期不做以下内容：

1. 不支持组织树拖拽换父节点。
2. 不支持任意可配置层级结构，仍固定为 `CAMPUS -> DEPT -> GROUP`。
3. 不强行将所有历史业务表立即细化到 `DEPT/GROUP` 粒度。
4. 不保留 `sys_user_campus` 作为权限来源的兼容分支。

## 3. 核心设计结论

### 3.1 权限范围统一定义

教务端账号的数据权限范围统一改为以下三种：

1. `ALL`
2. `ASSIGNED`
3. `SELF`

语义定义如下：

1. `ALL`
   - 可见全部数据。
   - 不参与组织树授权。
   - 不依赖 `sys_user_org_scope`。
2. `ASSIGNED`
   - 可见手动绑定的组织节点及其全部下级节点对应的数据集合。
   - 必须依赖 `sys_user_org_scope`。
   - 允许绑定多个组织节点。
3. `SELF`
   - 仅可见本人数据。
   - 不允许手动绑定组织树。

### 3.2 组织层级与权限范围解耦

以下概念必须分离：

1. `ALL / ASSIGNED / SELF` 是权限模式。
2. `CAMPUS / DEPT / GROUP` 是组织节点类型。

后续如果组织形态变化，例如新增更高层级或中间层级，只需要调整组织节点类型和树结构，不需要再改数据权限枚举。

### 3.3 校区信息降级为基础资料

本次改造后，校区信息不再作为数据权限过滤条件。

校区信息仅承担以下职责：

1. 用户基础资料展示。
2. 主归属组织反推顶层校区后的冗余存储。
3. 与旧业务表保持必要字段兼容。

校区信息不再承担以下职责：

1. 不再作为教务端账号可见范围来源。
2. 不再作为 `DataScopeInterceptor` 的过滤输入。
3. 不再通过 `sys_user_campus` 控制数据隔离。

## 4. 数据模型设计

### 4.1 新增组织节点表 `sys_org_node`

用于维护组织树结构。

建议字段如下：

1. `id` bigint 主键
2. `parent_id` bigint 父节点 ID，根节点可为 `0` 或 `NULL`
3. `node_type` tinyint 节点类型
   - `1` = `CAMPUS`
   - `2` = `DEPT`
   - `3` = `GROUP`
4. `code` varchar(50) 节点编码
5. `name` varchar(100) 节点名称
6. `campus_id` bigint 所属顶层校区 ID
7. `ancestors` varchar(500) 祖先路径，示例 `1,12,35`
8. `level` int 层级深度
9. `sort` int 排序号
10. `status` tinyint 状态
11. `remark` varchar(200) 备注
12. `created_at` bigint 创建时间
13. `updated_at` bigint 更新时间

建议约束如下：

1. `CAMPUS` 节点必须为根节点。
2. `DEPT` 父节点必须是 `CAMPUS`。
3. `GROUP` 父节点必须是 `DEPT`。
4. 同一父节点下 `code` 唯一。
5. 同一父节点下 `name` 唯一。
6. `campus_id` 必须始终指向所属顶层 `CAMPUS`。

建议索引如下：

1. `idx_sys_org_node_parent_id`
2. `idx_sys_org_node_campus_id`
3. `idx_sys_org_node_status`
4. `uk_sys_org_node_parent_id_code`
5. `uk_sys_org_node_parent_id_name`

### 4.2 新增用户组织授权表 `sys_user_org_scope`

用于代理教务端账号的组织权限绑定关系，并替代 `sys_user_campus` 成为数据隔离唯一来源。

建议字段如下：

1. `id` bigint 主键
2. `user_id` bigint 教务端账号 ID
3. `org_node_id` bigint 组织节点 ID
4. `is_primary` tinyint 是否主归属节点
5. `created_at` bigint 创建时间
6. `updated_at` bigint 更新时间

建议约束如下：

1. 唯一索引 `uk_sys_user_org_scope_user_id_org_node_id`
2. 一个用户最多仅允许一条 `is_primary = 1` 记录
3. `SELF` 用户不得存在有效组织授权
4. `ASSIGNED` 用户至少应存在一条组织授权
5. `ALL` 用户可无组织授权

建议索引如下：

1. `idx_sys_user_org_scope_org_node_id`
2. `idx_sys_user_org_scope_user_id_primary`

### 4.3 调整教务端用户表 `sys_internal_user`

建议增加或明确以下字段职责：

1. `data_scope_type`
   - 仅允许 `ALL / ASSIGNED / SELF`
2. `org_node_id`
   - 表示用户主归属组织节点
3. `campus_id`
   - 表示用户主归属组织反推出的顶层校区
   - 仅作为基础资料冗余存储，不参与权限过滤

说明：

1. `org_node_id` 用于表示账号属于哪个具体组织位置。
2. `campus_id` 用于兼容旧业务和页面展示。
3. 主归属节点变化时，必须同步更新 `org_node_id` 与 `campus_id`。

### 4.4 旧表 `sys_user_campus` 的定位

`sys_user_campus` 在本方案中的处理方式如下：

1. 从数据权限主链路中完全移除。
2. 不再被 `DataScopeInterceptor` 使用。
3. 不再作为教务端账号可见范围来源。
4. 如无其他历史功能依赖，可在迁移完成后逐步废弃。

## 5. 权限计算模型

### 5.1 可见范围计算规则

1. 用户为 `ALL` 时
   - 不拼接组织范围条件。
   - 默认可见全部目标数据。
2. 用户为 `SELF` 时
   - 仅允许查看自身数据。
3. 用户为 `ASSIGNED` 时
   - 读取 `sys_user_org_scope`。
   - 获取该用户绑定的所有组织节点。
   - 将所有绑定节点展开为“节点自身 + 全部下级节点”。
   - 对展开结果取并集后参与数据过滤。

### 5.2 父节点与子节点权限语义

组织树权限遵循以下规则：

1. 绑定 `CAMPUS` 节点
   - 可见该校区下所有部门和组。
2. 绑定 `DEPT` 节点
   - 可见该部门及其下所有组。
3. 绑定 `GROUP` 节点
   - 仅可见该组。

即：父节点绑定的可视权限等于其全部子节点可视权限的集合。

### 5.3 一期数据过滤落地方式

一期后端能力按两层设计：

1. 权限来源提升到组织节点级。
2. 具体业务过滤先按现有业务表实际字段落地。

说明如下：

1. 若业务表已具备 `org_node_id`，则可直接按组织节点过滤。
2. 若业务表当前仅具备 `campus_id`，则先将 `ASSIGNED` 权限节点折算为对应可见校区集合，再按 `campus_id` 过滤。

这意味着：

1. 一期的权限模型已经是组织树模型。
2. 但部分历史业务数据的实际过滤粒度仍可能暂时停留在校区级。
3. 后续业务表具备组织节点字段后，可自然升级到更细粒度。

## 6. 后端架构改造点

### 6.1 枚举改造

改造 `UserDataScopeType`，统一为以下三种：

1. `ALL`
2. `ASSIGNED`
3. `SELF`

要求如下：

1. 旧的 `SPECIFIED_CAMPUS` 不再保留为长期语义。
2. 数据迁移阶段可将旧值映射为 `ASSIGNED`。
3. 代码中不再出现“指定校区权限”的业务命名。

### 6.2 数据权限上下文改造

当前数据权限上下文仅围绕校区集合构建，需要扩展为围绕组织授权构建。

建议将 `DataScopeUserContext` 改造成包含以下信息：

1. `userId`
2. `userType`
3. `dataScopeType`
4. `primaryOrgNodeId`
5. `authorizedOrgNodeIds`
6. `authorizedCampusIds`

其中：

1. `authorizedOrgNodeIds` 用于支持未来按组织粒度过滤。
2. `authorizedCampusIds` 用于兼容一期中仍只按校区字段过滤的业务表。

### 6.3 `DataScopeInterceptor` 改造

改造目标如下：

1. 不再调用 `userCampusDao.listCampusIdsByUserId()` 获取权限范围。
2. 改为调用组织授权服务读取 `sys_user_org_scope`。
3. 对 `ASSIGNED` 用户先展开组织节点，再构建过滤上下文。

改造后职责如下：

1. 识别当前登录用户的数据权限类型。
2. 根据权限类型构建统一上下文。
3. 分发到对应 `DataScopeStrategy` 生成 SQL 条件。

### 6.4 `DataScopeStrategy` 改造

建议策略层收敛为三类：

1. `AllDataScopeStrategy`
2. `SelfDataScopeStrategy`
3. `AssignedDataScopeStrategy`

其中 `AssignedDataScopeStrategy` 不再依赖 `sys_user_campus`，而是只依赖组织授权上下文。

### 6.5 组织授权解析服务

建议新增独立服务，例如：`OrgDataScopeResolveService`。

职责如下：

1. 根据用户 ID 查询组织授权记录。
2. 找出主归属节点。
3. 递归或批量展开全部下级节点。
4. 汇总出最终可见 `orgNodeIds`。
5. 汇总出最终可见 `campusIds`。

该服务负责“算权限”，而不是由 SQL Strategy 自己回表查权限。

## 7. 用户组织绑定与资料同步规则

### 7.1 绑定资格规则

1. `SELF` 用户不具备手动绑定组织树资格。
2. `ASSIGNED` 用户具备手动绑定组织树资格。
3. `ALL` 用户默认可见全部数据，不要求绑定组织树。

### 7.2 主归属规则

1. 一个账户只能有一个主归属节点。
2. 主归属节点允许是 `CAMPUS`、`DEPT`、`GROUP` 任意一种。
3. 主归属节点所在的顶层校区同步为用户基础校区信息。

### 7.3 组织授权更新事务规则

更新用户组织授权时，必须在一个事务内完成以下步骤：

1. 校验用户存在且状态可操作。
2. 校验数据权限类型是否允许组织绑定。
3. 校验组织节点合法性与主归属节点唯一性。
4. 删除旧的 `sys_user_org_scope` 记录。
5. 写入新的 `sys_user_org_scope` 记录。
6. 根据主归属节点反查顶层校区。
7. 更新 `sys_internal_user.org_node_id`。
8. 更新 `sys_internal_user.campus_id`。
9. 清理用户快照缓存与权限缓存。

### 7.4 校区变化时的联动更新

当通过权限树修改 `sys_user_org_scope` 导致用户主归属校区变化时，必须同步处理：

1. 更新用户主归属组织字段。
2. 更新用户基础校区字段。
3. 清理并重建相关缓存。
4. 保证后续鉴权链路读取到的是新组织归属和新权限范围。

## 8. 缓存改造

### 8.1 用户快照缓存扩展

建议安全快照缓存至少包含：

1. `enabled`
2. `currentCampusId`
3. `primaryOrgNodeId`
4. `dataScopeType`

说明：

1. `currentCampusId` 仅表示用户基础资料中的当前归属校区。
2. `currentCampusId` 不等于数据权限范围。
3. `primaryOrgNodeId` 用于表达用户当前主归属位置。

### 8.2 缓存失效触发点

以下场景必须清理安全缓存：

1. 用户组织授权变更。
2. 用户数据权限类型变更。
3. 用户主归属组织变更。
4. 用户状态变更。
5. 用户角色变更。

建议复用现有 `InternalUserCacheCleanupService`，扩展其职责，而不是另起一套缓存清理机制。

## 9. 接口规划

### 9.1 组织树接口

建议新增以下接口：

1. `GET /admin/api/v1/org-tree`
   - 查询完整组织树
2. `GET /admin/api/v1/org-nodes/{id}`
   - 查询节点详情
3. `POST /admin/api/v1/org-nodes`
   - 创建节点
4. `PUT /admin/api/v1/org-nodes/{id}`
   - 修改节点
5. `DELETE /admin/api/v1/org-nodes/{id}`
   - 删除节点

### 9.2 组织绑定接口

建议新增以下接口：

1. `GET /admin/api/v1/org-nodes/{id}/users`
   - 查询节点已绑定账号
2. `PUT /admin/api/v1/org-nodes/{id}/users`
   - 覆盖更新节点绑定账号
3. `GET /admin/api/v1/org-accounts/options`
   - 查询可绑定账号选项
4. `PUT /admin/api/v1/internal-users/{userId}/org-scope`
   - 从账号页直接修改组织授权
5. `PUT /admin/api/v1/internal-users/{userId}/data-scope`
   - 修改用户数据权限模式

### 9.3 接口行为约束

1. 组织树接口本身必须受后台功能权限控制。
2. 组织树节点删除前必须校验无子节点、无绑定账号。
3. `SELF` 用户不得出现在可绑定列表中。
4. `ASSIGNED` 用户修改为 `SELF` 时，应清空组织授权。
5. `ALL` 用户不要求组织授权，但若存在历史绑定，建议同步清理。

## 10. 数据迁移方案

### 10.1 初始化组织树

迁移步骤如下：

1. 读取现有 `sys_campus`。
2. 为每个校区生成一个 `CAMPUS` 根节点写入 `sys_org_node`。
3. 初始化 `ancestors`、`level`、`campus_id` 等基础字段。

### 10.2 迁移旧用户校区绑定

若历史上教务端账号依赖 `sys_user_campus`，则迁移步骤如下：

1. 读取旧的用户校区绑定记录。
2. 将旧校区绑定转换为对应 `CAMPUS` 组织节点绑定。
3. 将旧主校区映射为 `is_primary = 1` 的组织授权记录。
4. 将旧 `SPECIFIED_CAMPUS` 用户的权限类型迁移为 `ASSIGNED`。

### 10.3 清理旧权限语义

迁移完成后：

1. 新代码不再使用 `SPECIFIED_CAMPUS`。
2. 新代码不再从 `sys_user_campus` 读取权限范围。
3. 新代码统一从 `sys_user_org_scope` 解析组织权限。

## 11. 一期实施顺序

建议按以下顺序实施：

1. 新增表结构
   - `sys_org_node`
   - `sys_user_org_scope`
   - `sys_internal_user` 补充归属字段
2. 初始化组织树基础数据
   - `sys_campus -> CAMPUS` 节点
3. 改造权限枚举与数据权限上下文
4. 改造 `DataScopeInterceptor` 与 `DataScopeStrategy`
5. 落地组织授权解析服务
6. 落地组织树管理接口
7. 落地组织树绑定账号接口
8. 落地缓存清理与用户资料同步
9. 执行历史数据迁移
10. 移除 `sys_user_campus` 在权限链路中的使用

## 12. 风险与注意事项

### 12.1 粒度风险

一期虽然权限来源已经变成组织树，但如果历史业务表仍只有 `campus_id` 字段，则实际过滤粒度仍可能先停留在校区级。

这不影响本次方案成立，但需要在需求沟通中明确：

1. 权限模型已支持组织树。
2. 实际过滤粒度是否能细到 `DEPT/GROUP`，取决于具体业务表是否具备组织维度字段。

### 12.2 主归属与可见范围混淆风险

必须明确：

1. `is_primary = 1` 表示用户属于哪里。
2. 其他绑定节点表示用户还能看哪里。

不能把“主归属”和“可见范围”混为一个概念。

### 12.3 组织树结构变更风险

一期建议不支持拖拽移动节点，原因如下：

1. 移动节点会影响整棵子树的 `ancestors`。
2. 移动节点会影响所有相关用户的授权范围。
3. 会显著增加缓存失效和数据一致性复杂度。

### 12.4 旧功能兼容风险

若系统仍存在读取 `sys_user_campus` 决定权限的旧代码，必须在切换前全部清理，否则会出现权限结果不一致。

## 13. 最终方案摘要

本次一期权限树改造的最终方向为：

1. 数据权限范围统一为 `ALL / ASSIGNED / SELF`。
2. 组织结构固定为 `CAMPUS / DEPT / GROUP`，但组织层级与权限模式解耦。
3. 新增 `sys_org_node` 维护组织树。
4. 新增 `sys_user_org_scope` 作为数据隔离唯一权限来源。
5. `sys_user_campus` 退出数据权限系统。
6. 校区信息仅作为基础资料保留，不参与权限过滤。
7. 通过权限树修改用户组织绑定时，同步更新用户归属字段与缓存。
8. 数据权限主链路继续复用现有 `DataScopeInterceptor` 架构，只是将“按校区过滤”升级为“按组织授权过滤”。

## 14. 已确认边界

以下边界已确认，后续实现按此执行，不再默认变更：

1. 教务账号必须且只能有一个主归属组织节点。
2. `sys_internal_user` 保留 `campus_id`，但仅作为基础资料冗余字段。
3. `ALL` 用户禁止出现在组织树绑定列表中，也不保留组织授权记录。
4. 用户组织授权支持双入口修改：
   - `org-tree` 页面
   - `org-account` 页面
5. 一期只管理教务账号的组织授权，不管理教师账号的组织归属。
6. 教师未来允许归属 `DEPT` 或 `GROUP`，但由于一期不修改 `sys_teacher_user`，教师真实组织归属过滤列为二期前置条件。
7. 学生后续通过 `teacher_id` 关联老师，但本方案一期不落学生与老师关系表改造。

3. 但由于一期不修改 `sys_teacher_user`，因此教师真实组织归属过滤不纳入一期实现。

因此一期实际落地原则为：

1. 教务账号自身列表、详情、可见范围过滤按组织树模型落地。
2. 其他仍只有 `campus_id` 的历史业务表继续按兼容方式过滤。
3. 教师真实 `DEPT/GROUP` 过滤在二期补 `org_node_id` 后再接入。

### 18.2 Mapper 注解扩展建议

当前 `@DataScope(tableAlias, scopeField)` 仅适合一条过滤字段，后续可能不够表达组织节点与校区兼容两种场景。

一期建议保持注解最小改动，但增加规范：

1. 若目标表按用户 ID 过滤，则 `scopeField` 表示用户 ID。
2. 若目标表按组织节点过滤，则 `scopeField` 表示 `org_node_id`。
3. 若目标表按校区兼容过滤，则 `scopeField` 表示 `campus_id`。

同时建议在文档中明确，`AssignedDataScopeStrategy` 需要识别目标字段语义，不能再沿用原 `sys_user_campus` 的 exists 模式。

若实现中发现单一 `scopeField` 难以表达，建议二选一：

1. 扩展 `@DataScope` 增加 `scopeType` 字段
2. 新增第二个注解专门处理组织维度过滤

一期优先建议方案 1。

## 19. 接口入参与校验细化

### 19.1 创建/编辑教务账号校验

建议校验规则：

1. `roleIds` 必填且去重。
2. `dataScopeType` 必须合法。
3. `primaryOrgNodeId` 必须存在。
4. `primaryOrgNodeId` 必须是启用状态节点。
5. `orgScopeNodeIds` 中节点必须全部存在且去重。
6. 若 `dataScopeType = ASSIGNED`
   - `orgScopeNodeIds` 必填
   - 必须包含 `primaryOrgNodeId`
7. 若 `dataScopeType = SELF`
   - `orgScopeNodeIds` 必须为空或后端自动忽略
8. 若 `dataScopeType = ALL`
   - `orgScopeNodeIds` 必须为空或后端自动忽略

### 19.2 创建/编辑组织节点校验

建议校验规则：

1. `CAMPUS` 节点不能通过普通新增接口创建，建议由校区初始化迁移生成，或由专门接口创建。
2. 创建 `DEPT` 时父节点必须为 `CAMPUS`。
3. 创建 `GROUP` 时父节点必须为 `DEPT`。
4. 编码与名称需做归一化校验。
5. 已删除节点不可作为父节点。
6. 停用父节点下不可新建启用子节点。

### 19.3 节点绑定账号校验

建议校验规则：

1. 只能绑定 `ASSIGNED` 用户。
2. `SELF` 用户不得绑定。
3. `ALL` 用户不得绑定。
4. 节点绑定账号接口若覆盖更新，必须重新计算这些账号的主归属合法性。
5. 若解绑后某个 `ASSIGNED` 用户已无任何授权节点，则应拦截或同步把其数据权限改为 `SELF`，该策略需实现时再确认。

说明：

1. 当前方案默认拦截“`ASSIGNED` 用户解绑后没有任何授权”的情况。
2. 不自动偷偷改成 `SELF`，避免后台行为超出操作者预期。

## 20. 迁移脚本思路细化

### 20.1 结构迁移顺序

建议顺序：

1. 新建 `sys_org_node`
2. 给 `sys_internal_user` 增加 `campus_id`、`org_node_id`
3. 新建 `sys_user_org_scope`
4. 初始化组织树根节点
5. 回填用户基础资料字段
6. 迁移旧校区绑定到组织授权
7. 切换代码读取逻辑

### 20.2 根节点初始化脚本思路

示例逻辑：

1. 遍历 `sys_campus`
2. 插入对应 `CAMPUS` 节点
3. `parent_id = 0`
4. `campus_id = sys_campus.id`
5. `level = 1`
6. `ancestors = ''`

### 20.3 用户组织授权迁移脚本思路

示例逻辑：

1. 将 `sys_user_campus` 中每条记录映射到对应 `CAMPUS` 节点
2. 插入 `sys_user_org_scope`
3. 原 `is_primary = 1` 映射为新表 `is_primary = 1`
4. 读取主归属节点回填 `sys_internal_user.org_node_id`
5. 读取对应 `campus_id` 回填 `sys_internal_user.campus_id`

### 20.4 历史脏数据处理建议

迁移前建议先检查以下问题：

1. 一个用户存在多个主校区
2. 一个用户没有任何校区绑定但数据权限是旧 `SPECIFIED_CAMPUS`
3. 绑定了已删除校区
4. `data_scope_type` 存在无效值

发现脏数据时，建议先人工修复或记录异常清单，不要在迁移脚本里静默吞掉。

## 21. 未决实现点

以下点已被显式保留为实现阶段再确认，不在本文档中擅自定死：

1. `SELF` 用户是否需要把主归属节点单独存入 `sys_user_org_scope`
   - 当前文档推荐不存，只存 `sys_internal_user.org_node_id`
2. `@DataScope` 是否扩展 `scopeType`
   - 当前文档建议在实现时优先评估后决定
3. 节点绑定账号接口是“覆盖整个节点绑定列表”还是“增量绑定/解绑”
   - 当前文档按覆盖式描述，若前端交互不同需再收敛
4. `CAMPUS` 节点是否允许直接从组织树界面新增
   - 当前文档偏向由校区管理初始化同步，不建议普通新增

## 22. 建议的下一步实现顺序

基于本细化方案，建议编码时按以下顺序推进：

1. 先改库表与初始化脚本
2. 再改枚举、Entity、DAO
3. 再改 `InternalUser` 创建/编辑/详情链路
4. 再改 `DataScopeInterceptor` 与缓存模型
5. 最后补组织树接口和迁移逻辑

这样可以先让数据模型闭环，再接入权限过滤，风险最小。
