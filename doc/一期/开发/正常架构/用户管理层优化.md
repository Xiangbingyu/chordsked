# 用户管理层优化

## 1. 背景与问题

当前教务端账号管理存在两个业务约束缺口：

1. 系统账户不应允许在后台账号管理页执行以下操作：
   - 修改账号
   - 修改状态
   - 重置密码
2. 发起请求的当前登录人，不应在“账号管理”链路中对自己的账号执行以上三类操作。

现状检查结果：

- `InternalUserUpdateServiceImpl` 只校验了“目标账号存在 + 当前登录人对目标账号有数据权限”，没有拦截“系统账户”与“本人账号”。
- `InternalUserResetPasswordServiceImpl` 同样没有拦截“系统账户”与“本人账号”。
- `InternalUserStatusUpdateServiceImpl` 只拦截了“禁用自己”，但没有拦截：
  - 修改自己状态中的其他场景
  - 对系统账户改状态
- `InternalUserQueryServiceImpl` 和 `InternalUserDetailQueryServiceImpl` 没有给前端返回“该账号是否系统账户 / 是否本人”的辅助标记，导致前端无法提前禁用按钮。

## 2. 对几个候选方案的评估

### 2.1 方案A：查询时直接不返回系统账户和本人

不建议作为主方案，原因如下：

- 这是“展示层过滤”，不是“安全层校验”，用户仍然可能绕过前端直接调用接口。
- 会导致列表总数、搜索结果、账号可见性与真实数据不一致，不利于运营排查。
- 系统账户和本人账号通常仍然需要“可见但不可操作”，完全隐藏会损失管理视角。
- 后端三个写接口仍然必须做兜底校验，因此即使隐藏列表，也不能省略后端改造。

结论：

- 不要把“查询过滤掉系统账户/本人”当作安全方案。
- 是否隐藏可作为产品展示策略单独讨论，但不能替代后端校验。

### 2.2 方案B：只在 VO 中增加“是否系统账户”字段

只能解决前端按钮禁用问题，不能解决接口直调风险。

结论：

- 可以做，但只能作为前端交互辅助。
- 不能代替后端统一校验服务。

### 2.3 方案C：新增统一校验服务，三个写接口统一接入

这是必须做的主方案。

优点：

- 安全边界在后端，前端是否禁用都不会突破规则。
- 三条链路共用一套规则，避免逻辑漂移。
- 后续如果新增“删除账号”“强制下线”等操作，也可以复用同一套校验能力。

结论：

- 推荐作为本期核心改造。

### 2.4 方案D：给账号增加“系统账户”持久化字段

这是长期最干净的建模方式，但属于中等改造。

优点：

- “系统账户”成为账号自身属性，语义最稳定。
- 不依赖用户名硬编码，也不依赖角色间接推断。
- 查询、详情、写操作都可以直接复用同一字段。

缺点：

- 需要改表、改 mapper、改 entity、改初始化数据。
- 当前问题如果想快速修复，成本略高。

结论：

- 作为中长期演进方案合理。
- 如果当前目标是快速闭环，建议先做“统一校验服务 + 前端辅助标记”。

## 3. 关于“系统账户如何判定”的建议

### 3.1 不建议直接复用 `preset-role-codes`

当前配置里：

- `chordsked.role.preset-role-codes = [ADMIN, OPERATOR]`

但从初始化数据看：

- `ADMIN` 是管理员角色
- `OPERATOR` 是普通教务运营角色

如果把“绑定预置角色”直接等同于“系统账户”，会把普通运营账号也误判为系统账户，导致这些账号都无法被修改。

因此：

- “系统预置角色”不等于“系统账户”
- 不能直接拿 `preset-role-codes` 做系统账户判定

### 3.2 本期推荐的判定方式

本期更推荐采用“新增专用受保护角色”方案，例如：

- `SYSTEM_ADMIN`

这里要特别区分两个概念：

- `AccountUserType.ADMIN` 是账号大类，表示教务端内部账号
- `SYSTEM_ADMIN` 应该是内部账号下的一个专用角色或身份标签，用于标记“受保护账户”

不建议把“系统管理员”建模为新的 `AccountUserType`，原因如下：

- 会牵动登录、鉴权、权限缓存、用户快照装载等主链路
- 现有教务端账号提供器 `InternalAccountProvider` 默认都按 `ADMIN` 大类装载
- 当前问题本质上是“内部账号中的一类特殊受保护对象”，不是新增账号体系

因此，本期更合适的做法是：

1. 在 `sys_role` 新增一个专用角色，例如 `SYSTEM_ADMIN`
2. 将系统管理员账号同时绑定：
   - `ADMIN`
   - `SYSTEM_ADMIN`
3. 后端通过“是否持有 `SYSTEM_ADMIN` 角色”来判定是否为受保护账户

这样做的好处：

- 语义清晰，不再依赖用户名
- 不会误伤普通 `ADMIN` 角色用户
- 不需要改登录主链路
- 后端查询和写操作都可统一按角色判定

进一步建议：

- `SYSTEM_ADMIN` 更适合作为“标记角色”
- 它本身不一定要承载完整业务权限
- 业务权限仍可继续由 `ADMIN` 角色提供

也就是说，更推荐：

- `ADMIN` 负责权限
- `SYSTEM_ADMIN` 负责“受保护身份标记”

而不是用 `SYSTEM_ADMIN` 完整替代 `ADMIN`。

这样可以避免：

- 权限复制
- 角色权限维护重复
- 后续菜单/接口授权分叉

如果后续确实希望“系统管理员”和“普通管理员”在权限上也有差异，再考虑单独给 `SYSTEM_ADMIN` 配权限集合。

### 3.3 配置建议

即使采用专用角色方案，也不建议直接复用 `preset-role-codes` 做保护判断。

建议新增独立配置，例如：

- `chordsked.role.protected-role-codes: [SYSTEM_ADMIN]`

这样可与现有：

- `preset-role-codes`

形成职责分离：

- `preset-role-codes`: 表示系统预置角色，控制是否允许删除/修改角色定义
- `protected-role-codes`: 表示受保护账户标记角色，控制是否允许修改账号/状态/密码

注意：

- “预置角色”与“受保护账户角色”可以重叠，但不应混为同一概念
- 如果后续系统账户不止一种，还可以继续扩展多个受保护角色

## 4. 推荐落地方案

### 4.1 总体原则

采用“两层防线”：

1. 后端统一校验服务做强约束
2. 查询/详情接口返回辅助标记给前端禁用按钮

其中：

- 后端校验是必须项
- 前端禁用只是体验优化

### 4.2 不建议从列表中移除系统账户和本人

推荐保持：

- 列表仍然返回系统账户
- 列表仍然返回本人账号

但同时返回标记字段，让前端禁用：

- 修改
- 禁用/启用
- 重置密码

理由：

- 数据可见，便于审计和识别
- 规则透明，用户知道“为什么不能点”
- 后端与前端职责清晰

### 4.3 给查询/详情 VO 增加辅助字段

建议在以下两个 VO 中增加字段：

- `InternalUserQueryResultVO`
- `InternalUserDetailResultVO`

建议新增：

- `private Boolean systemAccount;`
- `private Boolean currentUser;`

字段语义：

- `systemAccount`: 是否受保护系统账户
- `currentUser`: 是否当前登录人本人

前端规则：

- `systemAccount == true` 时，禁用三个操作按钮
- `currentUser == true` 时，禁用三个操作按钮

备注：

- 这两个字段可在 service 层组装，不一定需要改 SQL
- `currentUser` 可通过 `SecurityPrincipalUtils.getCurrentUserId()` 计算
- `systemAccount` 可通过“是否命中受保护角色”计算

### 4.4 新增统一校验服务

建议新增服务：

- `InternalUserOperationGuardService`

建议职责：

1. 校验目标账号是否存在
2. 校验当前登录人是否对目标账号有数据权限
3. 校验目标账号是否为系统账户
4. 校验目标账号是否为当前登录人本人
5. 返回目标账号实体，供后续业务复用

建议接口示意：

```java
public interface InternalUserOperationGuardService {
    InternalUserEntity validateManageActionTarget(Long targetUserId, String actionName);
}
```

建议实现逻辑示意：

```java
1. 校验 userId > 0
2. targetUser = internalUserDao.getById(userId)
3. targetUser == null -> 抛业务异常
4. !internalUserDao.existsAccessibleById(userId) -> 抛 FORBIDDEN
5. targetUser 持有 protected-role-codes 中任一角色 -> 抛业务异常
6. SecurityPrincipalUtils.getCurrentUserId() == userId -> 抛业务异常
7. 返回 targetUser
```

建议异常文案：

- 系统账户不允许在账号管理中执行该操作
- 不能在账号管理中操作自己的账号

说明：

- 这里不要把“本人校验”写成只拦截禁用自己
- 应改为对三类操作统一拦截本人账号

### 4.5 三个写服务接入统一校验

以下三个实现都应接入统一校验服务：

- `InternalUserUpdateServiceImpl`
- `InternalUserStatusUpdateServiceImpl`
- `InternalUserResetPasswordServiceImpl`

接入方式建议：

#### `InternalUserUpdateServiceImpl`

将当前：

- `getById`
- `existsAccessibleById`

改为：

- 直接调用 `internalUserOperationGuardService.validateManageActionTarget(userId, "修改账号")`

然后复用返回的 `targetUser / existingUser`。

#### `InternalUserStatusUpdateServiceImpl`

当前只拦截“禁用自己”，需要改为：

- 先调用统一校验服务
- 再执行状态变更专属规则
- 保留“至少保留一个启用管理员账号”的现有规则

也就是说：

- “本人不可操作”
- “系统账户不可操作”
- “至少保留一个启用管理员账号”

三条规则并存，不冲突。

#### `InternalUserResetPasswordServiceImpl`

将当前：

- `getById`
- `existsAccessibleById`

改为统一走 `internalUserOperationGuardService`

这样可以补上：

- 不能重置系统账户密码
- 不能重置自己密码

## 5. 查询与详情链路如何赋值标记

### 5.1 `InternalUserQueryServiceImpl`

在现有 `fillRoleIds(items)` 之后，增加类似处理：

```java
Long currentUserId = SecurityPrincipalUtils.getCurrentUserId();
Set<String> protectedUsernames = ...
for (InternalUserQueryResultVO item : items) {
    item.setCurrentUser(Objects.equals(item.getId(), currentUserId));
    item.setSystemAccount(protectedUsernames.contains(trimLower(item.getUsername())));
}
```

### 5.2 `InternalUserDetailQueryServiceImpl`

查询详情后同样补充：

- `detail.setCurrentUser(...)`
- `detail.setSystemAccount(...)`

这样前端列表和详情弹层规则保持一致。

## 7. 是否需要改表

### 本期建议

本期可以先不改表，先走：

- 专用受保护角色
- 统一校验服务
- 查询/详情返回辅助标记

这样能以最小成本解决当前问题。

### 中长期建议

如果后续有以下诉求，建议升级为表字段方案：

- 系统账户不止一个
- 不同环境系统账户不同
- 系统账户需要在后台可配置
- 审计日志或导出中需要明确标识系统账户

建议届时在 `sys_internal_user` 增加：

- `is_system` 或 `is_builtin`

并同步修改：

- `schema.sql`
- `data.sql`
- `InternalUserEntity`
- `InternalUserMapper.xml`
- `InternalUserQueryResultVO`
- `InternalUserDetailResultVO`
- 统一校验服务

## 8. 最终建议结论

结论如下：

1. 不建议直接在查询接口中过滤掉系统账户和本人账号。
2. 可以在 `InternalUserQueryResultVO`、`InternalUserDetailResultVO` 中增加辅助字段，但这不是安全边界，只是前端体验增强。
3. 必须新增统一校验服务，并在“修改 / 改状态 / 重置密码”三个写服务中统一接入。
4. “系统账户”本期不要直接复用 `preset-role-codes` 判断，推荐新增专用受保护角色，例如 `SYSTEM_ADMIN`。
5. 更推荐将 `SYSTEM_ADMIN` 作为“标记角色”，与 `ADMIN` 权限角色并存，而不是直接把 `ADMIN` 当受保护账户标识。
6. 可新增 `protected-role-codes` 配置，与 `preset-role-codes` 分离管理。
7. 长期最优方案仍然是给 `sys_internal_user` 增加持久化的系统账户标记字段。
8. 如果未来允许用户改自己的姓名、手机号、头像，应通过“个人中心”独立接口实现，不应复用管理员账号管理接口。

## 9. 推荐本期实施顺序

1. 扩展角色配置，增加 `protected-role-codes`
2. 新增 `InternalUserOperationGuardService`
3. 改造三个写服务统一接入校验
4. 给 Query/Detail VO 增加 `systemAccount`、`currentUser`
5. 在 QueryService / DetailQueryService 中填充标记
6. 初始化数据新增 `SYSTEM_ADMIN` 并绑定系统管理员账号
7. 前端根据标记禁用三个操作按钮
8. 补充单元测试/集成测试，覆盖：
   - 修改系统账户失败
   - 修改本人失败
   - 改状态系统账户失败
   - 改状态本人失败
   - 重置系统账户失败
   - 重置本人失败
