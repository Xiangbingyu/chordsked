> 对照文档：`00-总体架构.md` / `02-授权与数据隔离设计.md` / `04-审计日志模块设计.md` / `06-高可用与基础设施设计.md`

## 一、本轮复检结论

### 1.1 总体判断

当前 `InternalUserController -> Service -> DAO -> Mapper/XML -> DataScopeInterceptor` 主链路已经成型，**核心分层、鉴权、数据隔离、统一返回、事务边界**基本符合设计文档要求，具备继续迭代的基础。

但与架构文档相比，仍存在以下几类偏差：

1. **仍有一个会直接影响正确性的缺陷未修复**：`DEPARTMENT_AND_SUBORDINATE(2)` 枚举仍然没有对应策略实现。
2. **审计日志链路是“手动记录 + 事务回调保存”**，并非文档要求的 **AOP + 异步** 方案。
3. **高可用基础设施落地不足**：当前链路仍未接入 `@Idempotent`，TraceId 也仅实现了 `RequestId` 版本，未完全对齐设计稿。

### 1.2 各设计文档符合度总览

| 设计文档 | 符合度 | 本轮结论 |
|----------|--------|----------|
| `02-授权与数据隔离设计.md` | **88%** | JWT 路由、`@PreAuthorize`、`DataScope` 策略模式和 SQL 注入点已落地；部门策略缺失，ThreadLocal 方案未严格按文档实现 |
| `00-总体架构.md` | **89%** | 分层清晰，统一响应、统一异常、事务边界、统一用户服务路由均已具备 |
| `04-审计日志模块设计.md` | **72%** | 手动审计记录可用，且区分成功/失败事务时机；但未实现 `@AuditLog` AOP 自动化，也未异步化 |
| `06-高可用与基础设施设计.md` | **58%** | 已有 `RequestIdFilter` 雏形；但幂等、防重、限流、分布式 ID、标准 TraceId 方案仍未完成 |

### 1.3 相比上轮，本轮确认到的变化

1. **`DEPARTMENT_AND_SUBORDINATE(2)` 缺失策略的问题仍然存在**，并未修复。
2. **审计日志是否异步处理已可明确判定为“未异步”**，当前实现未使用 `@Async`、事件驱动或消息队列。
3. **链路追踪不再是“待确认”状态**，当前存在 `RequestIdFilter`，但实现的是 `X-Request-Id + MDC(requestId)`，并非设计稿中的 `X-Trace-Id + MDC(traceId)`。

## 二、已符合或基本符合的设计点

### 2.1 对 `00-总体架构.md` 的符合项

1. **分层方向正确**  
   `InternalUserController` 只负责入参接收和响应包装，业务进入 `InternalUserCreateServiceImpl` / `InternalUserQueryServiceImpl`，数据访问走 `InternalUserDao` 和 MyBatis Mapper，符合 `Controller -> Service -> DAO -> Database` 的分层约束。

2. **统一返回结构已落实**  
   Controller 层统一返回 `ApiResponse<?>`，分页查询返回 `ApiResponse<PageResult<...>>`，符合总体架构中“接口统一返回格式”的要求。

3. **统一异常处理已落实**  
   `GlobalExceptionHandler` 已集中处理 `BusinessException`、参数校验异常和兜底异常，符合“全局异常处理机制”设计。

4. **事务边界在 Service 层**  
   创建账号由 `InternalUserCreateServiceImpl#create()` 使用 `@Transactional(rollbackFor = Exception.class)` 统一包裹，符合总体架构对事务边界的要求。

5. **统一用户服务路由思路已落地**  
   `JwtAuthenticationFilter` 解析 JWT 后，调用 `MultiAccountUserDetailsService`，再按 `userType` 路由到 `InternalAccountProvider` / `TeacherAccountProvider` / `StudentAccountProvider`，与“账号类型注册制”的总体设计一致。

### 2.2 对 `02-授权与数据隔离设计.md` 的符合项

1. **鉴权主链路与文档基本一致**  
   当前链路已具备：JWT 解析 -> 多账号路由装载 `UserDetails` -> 写入 `SecurityContext` -> Controller 层 `@PreAuthorize` 权限校验。

2. **DataScope 组件采用了策略模式**  
   `DataScopeInterceptor` 通过 `Map<UserDataScopeType, DataScopeStrategy>` 进行策略分发，已经具备 `All` / `Campus` / `Self` 三种实现，核心结构与文档一致。

3. **Mapper 层按注解精确拦截**  
   `InternalUserMapper#listByQuery()` 和 `countByQuery()` 已标注 `@DataScope(tableAlias = "u", scopeField = "id")`，并在 XML 中预留 `/*DATA_SCOPE*/` 注入点，能够做到对指定查询精确拦截。

4. **数据权限上下文能够从登录态还原**  
   `InternalAccountProvider` 会装载 `dataScopeType` 与主校区信息，`DataScopeInterceptor` 再从 `SecurityContextHolder` 中读取 `ChordSkedUserDetails` 并拼装 `DataScopeUserContext`，查询链路是通的。

### 2.3 对 `04-审计日志模块设计.md` 的已落地点

1. **已存在独立审计日志服务**  
   当前通过 `AuditLogService#record()` 手动写入审计日志，说明“审计日志独立于普通业务逻辑”的方向是成立的。

2. **已记录操作者与请求环境信息**  
   `AuditLogRequestUtils` 会采集 `userId`、`userType`、`userName`、`requestUri`、`requestMethod`、`requestIp`、`userAgent`，覆盖了设计稿中的核心字段。

3. **成功与失败日志的事务时机做了区分**  
   `AuditLogServiceImpl` 对成功日志使用 `afterCommit()`，对失败日志使用 `afterCompletion()` 且仅在未提交时落库，这一点比简单同步写库更稳妥。

## 三、必须修复（影响正确性或直接影响链路可靠性）

### 3.1 [高] ~~`DEPARTMENT_AND_SUBORDINATE(2)` 枚举仍无对应策略实现~~ ✅ **已解决**

**位置**：
- `backend/src/main/java/com/chordsked/backend/model/enums/UserDataScopeType.java`
- `backend/src/main/java/com/chordsked/backend/datascope/interceptor/DataScopeInterceptor.java`
- `backend/src/main/java/com/chordsked/backend/datascope/strategy/`

**原问题描述**：
`UserDataScopeType` 原定义了 4 种数据权限类型，其中 `DEPARTMENT_AND_SUBORDINATE(2)` 无对应策略实现，会导致运行期异常。

**解决方案（2026-04-23 已执行）**：
采用 **方案 B：删除枚举值 + 文档说明**。

- 从 `UserDataScopeType` 枚举中移除了 `DEPARTMENT_AND_SUBORDINATE(2)`，当前仅保留 3 种有效类型：
  - `ALL_COMPANY(1)`
  - `SELF_ONLY(3)`
  - `SPECIFIED_CAMPUS(4)`
- 后续若需支持部门维度数据权限，需补齐 `DeptDataScopeStrategy` 并恢复该枚举值

**状态**：✅ **已关闭**

### 3.2 [高] ~~`POST /admin/api/v1/internal-users` 仍缺少幂等保护~~ ✅ **已解决**

**位置**：
- `backend/src/main/java/com/chordsked/backend/controller/InternalUserController.java`
- `backend/src/main/java/com/chordsked/backend/idempotent/` (幂等框架层)

**原问题描述**：
`06-高可用与基础设施设计.md` 明确要求对敏感写操作提供基于 Redis + Lua 的防重复提交能力。

**解决方案（2026-04-23 确认已实现）**：

经核查，项目已具备完整的幂等框架实现：

1. **`@Idempotent` 注解** - 标记需要防重复提交的接口
2. **`IdempotentInterceptor`** - 基于 Lua 脚本实现原子性 SETNX + EXPIRE
3. **`CachedBodyFilter`** - 最高优先级 Filter，缓存 POST/PUT/PATCH 请求体
4. **`CachedBodyHttpServletRequest`** - 可重复读请求包装类
5. **`IdempotentMvcConfig`** - 注册 MVC 拦截器，拦截 `/admin/api/v1/**` 路径
6. **`IdempotentProperties`** - 独立配置类，使用 `chordsked.security.idempotent.*` 前缀管理幂等开关、过期时间和 Key 前缀

`InternalUserController.createInternalUser()` 已添加注解：
```java
@PostMapping("/internal-users")
@Idempotent(expireSeconds = 5, message = "请勿重复提交创建请求")
@PreAuthorize("hasAuthority('admin:user:create')")
```

**状态**：✅ **已关闭**

## 四、建议改进（影响设计完整性）

### 4.1 [低|暂缓] DataScope 的用户上下文来源与设计稿不完全一致

**设计稿要求**：
`02-授权与数据隔离设计.md` 描述的是“拦截器放行后将 `UserContext` 存入 ThreadLocal，再由 MyBatis 数据权限拦截器读取”。

**当前实现**：
`DataScopeInterceptor` 直接从 `SecurityContextHolder` 读取 `ChordSkedUserDetails`，并在拦截器内部按需查询校区信息。

**判断**：
- 功能上可用，当前并不构成 bug。
- 但这意味着数据权限组件与 Spring Security 上下文发生了更强耦合，和文档中的“ThreadLocal 中立上下文”并不完全一致。

**本阶段决策（2026-04-23）**：
- 该项暂不改造，保持现状。
- 原因：当前链路稳定可用，且短期收益低于审计异步化、TraceId 统一等更高优先级事项。

**优先级**：低（暂缓）

### 4.6 [中] ~~TraceId 方案仅完成了 `RequestId` 版本，未完全对齐设计稿~~ ✅ **已解决**

**位置**：
- `backend/src/main/java/com/chordsked/backend/config/RequestIdFilter.java`
- `backend/src/main/resources/common/application-common.yml`

**解决方案（2026-04-23 已执行）**：
已完成 TraceId 兼容迁移改造，按“新协议优先 + 旧协议兼容”模式落地。

- `RequestIdFilter`：
  - 优先读取 `X-Trace-Id`，兼容回退读取 `X-Request-Id`
  - 两者缺失时自动生成 ID

  - MDC 同时写入 `traceId`（新）与 `requestId`（兼容）
- `application-common.yml`：
  - 日志 pattern 同时输出 `%X{traceId}` 与 `%X{requestId}`，保障迁移期检索连续性
