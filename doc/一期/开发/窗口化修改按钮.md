# 窗口化修改按钮实现方案

## 1. 目标

将 `e:\Github\chordsked\frontend\src\features\admin\org\pages\AccountPage.tsx` 当前基于 `window.prompt` 的账号修改交互，改造成页面内弹窗表单。

弹窗需要支持修改以下字段：

- 账户姓名 `name`
- 头像 URL `avatar`
- 联系方式 `phone`
- 可分配校区 `campusIds`
- 主校区 `primaryCampusId`
- 绑定角色 `roleIds`
- 数据范围 `dataScopeType`

约束要求：

- `campusIds` 通过多选组件修改
- `primaryCampusId` 必须从当前选中的 `campusIds` 中选择
- 当 `campusIds` 变化时，需要联动校验或修正 `primaryCampusId`
- 弹窗风格保持与当前页面按钮/卡片风格一致，使用当前页已有的暖色系、圆角、浅边框设计
- 受保护账号（`systemAccount = true`）和当前登录人（`currentUser = true`）仍然不可修改

1. 先请求账号详情
2. 用 `window.prompt` 输入姓名和手机号
3. 再把详情中的 `avatar`、`roleIds`、`campusIds`、`primaryCampusId`、`dataScopeType` 原样带回更新接口

- 交互粗糙，无法一次性编辑多个字段
- 无法可视化选择角色、校区、数据范围
- 不能直观看到“可分配校区集合”和“主校区”的关系

### 2.2 后端现状

字段要求如下：

- `primaryCampusId` 必须包含在 `campusIds` 中

此外，当前详情接口仍会返回：

- `campusIds`

## 3. 方案结论

### 3.1 前端窗口化修改可以立即做

可以直接按当前后端协议实现，不需要改 DTO。

实现方式：

- 弹窗中提供 `campusIds` 多选
- 弹窗中提供 `primaryCampusId` 单选
- `primaryCampusId` 的候选项只展示当前已选中的 `campusIds`
- 提交时按真实表单值原样提交 `campusIds` 与 `primaryCampusId`

这样完全符合现有后端校验，不需要做额外兼容映射。

### 3.2 `InternalUserCampusOptionQueryService` 现在不建议直接删除

当前不建议直接删除：

- 因为前端弹窗中的“可分配校区多选”和“主校区单选”都需要它提供基础数据
- 当前项目里没有别的可复用通用校区查询接口
- 一旦直接删除，前端将失去所有校区选项来源

正确做法应是二选一：

1. 保留现有服务与接口，继续作为“校区选择数据源”
2. 先新增或改造成“通用校区选项服务”，再删除当前 `internal-user` 专属命名的服务

### 3.3 你不需要再额外新增一套“获取所有校区”的重复服务

不需要新增重复能力。

因为当前这个服务本质上已经在做“获取未删除校区列表”：

- [InternalUserCampusOptionQueryServiceImpl.java](file:///e:/Github/chordsked/backend/src/main/java/com/chordsked/backend/service/internaluser/impl/InternalUserCampusOptionQueryServiceImpl.java)

更合理的处理方式是：

- 短期：直接复用现有接口
- 中期：把它重命名/上移为更通用的校区选项查询能力，而不是重新再写一套

这一步不涉及业务模型变化，风险相对较低。

## 5. 前端详细设计

## 5.1 新增状态

建议在 `AccountPage.tsx` 中增加以下状态：

```ts
type AccountEditFormState = {
  userId: number
  username: string
  name: string
  avatar: string
  phone: string
  campusIds: number[]
  primaryCampusId: number | null
  roleIds: number[]
  dataScopeType: UserDataScopeType | null
}
```

页面状态建议新增：

```ts
const [editModalOpen, setEditModalOpen] = useState(false)
const [editSubmitting, setEditSubmitting] = useState(false)
const [editLoading, setEditLoading] = useState(false)
const [editForm, setEditForm] = useState<AccountEditFormState | null>(null)
const [campusOptions, setCampusOptions] = useState<InternalUserCampusOptionVO[]>([])
const [campusOptionsLoading, setCampusOptionsLoading] = useState(false)
```

### 5.2 进入弹窗流程

点击“修改”按钮后：

1. 校验 `systemAccount/currentUser`
2. 打开 loading
3. 并行加载：
   - `getInternalUserDetail(row.id)`
   - `listInternalUserCampusOptions()`
   - 角色列表如果页面未缓存则复用现有 `roles`
4. 将详情数据填入表单
5. 打开弹窗

说明：

- 角色列表页面当前已经加载过，可直接复用 `roles`
- 校区列表需要额外加载，因为当前页尚未拉取

### 5.3 弹窗 UI 结构

建议使用原生 React + 当前页样式风格实现轻量弹窗，避免突然切换到完全不同视觉体系。

推荐结构：

- 遮罩层：半透明深色背景
- 弹窗容器：白底、圆角 `16px`
- 标题区：`编辑账号`
- 正文区：表单栅格布局
- 底部操作区：`取消` / `保存`

建议字段布局：

- 第一行：账号名（只读）、姓名
- 第二行：手机号、头像 URL
- 第三行：可分配校区（多选）
- 第四行：主校区、数据范围
- 第五行：绑定角色（多选）

推荐文案：

- 标题：`编辑账号`
- 副标题：`更新账号基础信息、可分配校区、主校区、角色和数据范围`

### 5.4 字段组件建议

建议字段类型如下：

- `username`：只读文本
- `name`：文本输入框
- `avatar`：文本输入框
- `phone`：文本输入框
- `campusIds`：多选下拉或复选框组
- `primaryCampusId`：单选下拉
- `roleIds`：多选复选框组或多选下拉
- `dataScopeType`：单选下拉

数据范围可选项：

```ts
[
  { value: 1, label: '全部校区' },
  { value: 3, label: '仅本人' },
  { value: 4, label: '指定校区' },
]
```

说明：

- `dataScopeType = 4` 时，业务语义仍然是“指定校区”
- 它应对应当前表单中选择的 `campusIds`
- `primaryCampusId` 仅表示这些校区中的主校区

### 5.5 前端校验

保存前做以下校验：

- `name.trim()` 非空
- `phone.trim()` 非空
- `phone` 满足手机号格式
- `campusIds.length > 0`
- `primaryCampusId` 非空
- `primaryCampusId` 必须存在于 `campusIds`
- `roleIds.length > 0`
- `dataScopeType` 非空
- `avatar` 允许空字符串，提交时转成 `undefined`

联动规则建议：

- 当用户取消选中当前 `primaryCampusId` 所在校区时，立即清空 `primaryCampusId`
- 或者自动将 `primaryCampusId` 切换为 `campusIds` 中第一个值
- 更推荐第一种，避免静默改值导致误操作

### 5.6 提交逻辑

调用：

- [internalUserService.ts](file:///e:/Github/chordsked/frontend/src/services/internalUserService.ts)

请求体建议如下：

```ts
await updateInternalUser(editForm.userId, {
  phone: editForm.phone.trim(),
  name: editForm.name.trim(),
  avatar: editForm.avatar.trim() || undefined,
  roleIds: editForm.roleIds,
  campusIds: editForm.campusIds,
  primaryCampusId: editForm.primaryCampusId!,
  dataScopeType: editForm.dataScopeType!,
})
```

成功后：

1. 关闭弹窗
2. 刷新列表 `loadAccounts()`
3. 提示 `账号 xxx 修改成功`

失败后：

- 在弹窗内或页面顶部显示错误信息

## 6. 后端详细建议

### 6.1 对本次窗口化需求，后端最小改动方案

如果本次只做“窗口化修改按钮”，后端可以不改。

原因：

- 现有更新接口已经能满足
- 当前 DTO 本身就支持 `campusIds + primaryCampusId`
- 业务层不需要额外新增接口

### 6.2 `InternalUserCampusOptionQueryService` 是否可以删除

结论：现在不能直接删。

原因：

- 前端校区多选和主校区单选仍然依赖“获取可选校区列表”
- 当前系统没有通用的校区列表 API 替代
- 删除会导致前端无法加载校区选项

更推荐的改法：

- 将其保留，但可考虑后续重命名为更通用的服务，例如：
  - `CampusOptionQueryService`
  - `CampusSelectorQueryService`
- 控制器接口也可后续迁移为：
  - `GET /admin/api/v1/campuses/options`

这样语义会比 `internal-users/campus-options` 更通用。

### 6.3 是否需要新增一个获取所有校区的服务

结论：不需要新增“重复服务”。

你真正需要的是“保留一个可复用的校区选项服务”。

建议：

- 不新增重复实现
- 直接复用当前能力
- 如果嫌命名不合适，就做“重命名/迁移”，不要“新建一套再并存”

### 6.4 本轮后端需要关注但不一定改动的点

虽然本轮可不改后端，但前端实现时应明确依赖以下既有规则：

- `campusIds` 不能为空
- `primaryCampusId` 必须包含在 `campusIds` 中
- `campusIds` 中每个校区都必须真实存在

如后续要增强体验，可考虑新增但不是必须的能力：

- 更轻量的角色选项接口
- 更通用命名的校区选项接口
- 详情接口里补充更直接的表单展示字段

## 8. 本次建议的最终结论

### 建议 1

先实现前端弹窗修改，不改后端 DTO。

### 建议 2

前端界面保留两个校区字段：

- `campusIds` 作为多选可分配校区
- `primaryCampusId` 作为单选主校区

### 建议 3

`InternalUserCampusOptionQueryService` 和 `InternalUserCampusOptionQueryServiceImpl` 现在不要直接删除。

### 建议 4

不需要新写一套“获取所有校区”的重复服务，直接复用当前校区选项接口即可；如果要整理架构，建议做重命名迁移，而不是新增并存。

### 建议 5

本轮不建议再做“删除 `campusIds`”方向的收敛，当前双字段模型与现有后端和数据范围语义是匹配的。
