# 06-高可用与基础设施设计

本部分设计涵盖支撑系统高并发、高可用及可观测性的底层核心组件。

## 1. 全局幂等性与防重复提交设计

**场景**：前端快速双击、网络超时重试等情况会导致敏感操作（如用户创建、排课等）被重复执行。
**设计**：提供基于 Redis + Lua 脚本的 `@Idempotent` 注解，实现细粒度的防重拦截。

### 1.1 幂等性组件类图

```mermaid
classDiagram
    class IdempotentInterceptor {
        -StringRedisTemplate redisTemplate
        +preHandle(HttpServletRequest req) boolean
        -generateKey(HttpServletRequest req, Idempotent anno) String
    }
    
    class Idempotent {
        <<annotation>>
        +int expireTime() default 3
        +String message() default "请勿重复操作"
    }

    IdempotentInterceptor ..> Idempotent : 解析注解
```

### 1.2 执行流程 (Lua 脚本保证原子性)

```mermaid
sequenceDiagram
    participant Client as 客户端
    participant Interceptor as 幂等拦截器
    participant Redis as Redis集群
    participant Controller as 业务控制器

    Client->>Interceptor: 发起 POST /user/create
    Interceptor->>Interceptor: 解析 @Idempotent 注解
    Interceptor->>Interceptor: 根据 {User_ID}:{URI}:{MD5(Body)} 生成唯一 Key
    
    Interceptor->>Redis: 执行 Lua 脚本 (SETNX + EXPIRE 原子操作)
    alt 成功获取锁 (首次请求)
        Redis-->>Interceptor: 返回 1
        Interceptor->>Controller: 放行请求，执行业务
        Controller-->>Client: 返回成功结果
    else 锁已存在 (重复请求)
        Redis-->>Interceptor: 返回 0
        Interceptor-->>Client: 抛出异常 (请勿重复操作)
    end
```

## 2. TraceId 链路追踪机制

**场景**：微服务或多模块下，由于日志交织，极难排查单个用户的请求生命周期。
**设计**：通过 `Filter` 和 `MDC` 实现全链路的 TraceId 透传。

### 2.1 核心执行流程

```mermaid
sequenceDiagram
    participant Client as 客户端
    participant TraceFilter as TraceIdFilter (网关/入口)
    participant MDC as ThreadLocal (MDC)
    participant Service as 业务层
    participant Logger as Logback / Log4j2

    Client->>TraceFilter: 发起请求 (Header: X-Trace-Id)
    
    alt 包含 TraceId
        TraceFilter->>TraceFilter: 提取 TraceId
    else 不包含
        TraceFilter->>TraceFilter: UUID.randomUUID() 生成新 TraceId
    end
    
    TraceFilter->>MDC: MDC.put("traceId", traceId)
    TraceFilter->>Service: 继续执行过滤链
    
    Service->>Logger: log.info("处理业务逻辑")
    Logger->>MDC: 读取 %X{traceId}
    Logger->>Logger: 格式化输出: [a1b2c3d4] 处理业务逻辑
    
    Service-->>TraceFilter: 返回 ResultDTO
    TraceFilter->>MDC: MDC.remove("traceId") (防止内存泄漏)
    TraceFilter-->>Client: 响应 Header 附加 X-Trace-Id
```

## 3. 统一 ID 生成器设计

**场景**：MySQL 自增主键在多实例或未来分库分表场景下会产生冲突，且容易暴露业务数据量。
**设计**：引入基于雪花算法（Snowflake）或 Redis 号段的分布式 ID 生成器，无缝集成到 MyBatis-Plus。

### 3.1 核心类图

```mermaid
classDiagram
    class IdentifierGenerator {
        <<interface>>
        +nextId(Object entity) Number
    }
    
    class CustomSnowflakeGenerator {
        -long workerId
        -long dataCenterId
        +nextId(Object entity) Number
    }
    
    class MyBatisPlusConfig {
        +identifierGenerator() IdentifierGenerator
    }

    IdentifierGenerator <|.. CustomSnowflakeGenerator
    MyBatisPlusConfig ..> CustomSnowflakeGenerator : 注入容器
```
*(注：为防止前端 JS 丢失 64 位整型精度，所有实体类的 `Long id` 需打上 `@JsonSerialize(using = ToStringSerializer.class)` 标签。)*

## 4. API 版本管理

**场景**：微信小程序端无法强制用户同步更新，后端接口升级时必须兼容旧版本。
**设计**：基于 URI 路径（如 `/v1/`, `/v2/`）或自定义的 `RequestMappingHandlerMapping` 实现多版本控制。

```mermaid
classDiagram
    class RequestMappingHandlerMapping {
        +getMappingForMethod() RequestMappingInfo
    }
    
    class ApiVersionHandlerMapping {
        +getMappingForMethod() RequestMappingInfo
        -createApiVersionInfo(ApiVersion anno) RequestCondition
    }
    
    class ApiVersion {
        <<annotation>>
        +int value()
    }

    RequestMappingHandlerMapping <|-- ApiVersionHandlerMapping
    ApiVersionHandlerMapping ..> ApiVersion : 解析
```

## 5. 限流熔断机制

**场景**：防范恶意刷短信接口（浪费资金）及账号密码暴力破解。
**设计**：基于 Redisson 或 Sentinel 实现分布式限流。

### 5.1 限流时序逻辑 (防刷短信示例)

```mermaid
sequenceDiagram
    participant Client as 客户端
    participant RateLimitFilter as @RateLimit 拦截器
    participant Redis as Redis (令牌桶/计数器)
    participant SmsService as 短信服务

    Client->>RateLimitFilter: POST /sms/send
    RateLimitFilter->>RateLimitFilter: 解析注解 @RateLimit(key="sms:{IP}", limit=1, time=60)
    RateLimitFilter->>Redis: incr(key) 并 expire(60s)
    
    Redis-->>RateLimitFilter: 返回当前计数值
    
    alt count <= 1
        RateLimitFilter->>SmsService: 放行
        SmsService-->>Client: 发送成功
    else count > 1
        RateLimitFilter-->>Client: 抛出 RateLimitException (请求过于频繁)
    end
```

## 6. 数据字典统一管理

**场景**：状态枚举（如授课类型 1:一对一, 2:小班）硬编码会导致多端文案不一致，修改成本高。
**设计**：将基础配置收敛到 `sys_dict` 和 `sys_dict_item` 表，配合 Redis 缓存供前端动态渲染。

### 6.1 字典管理类图

```mermaid
classDiagram
    class DictService {
        -RedisTemplate redisTemplate
        -DictMapper mapper
        +getDictList(String dictCode) List~DictItemDTO~
        +refreshCache()
    }
    
    class SysDict {
        -String dictCode "如: TEACHER_LEVEL"
        -String dictName "教师等级"
    }
    
    class SysDictItem {
        -String dictCode
        -String itemValue "如: 1"
        -String itemLabel "如: 初级"
        -Integer sortOrder
    }
    
    DictService --> SysDict
    DictService --> SysDictItem
```
