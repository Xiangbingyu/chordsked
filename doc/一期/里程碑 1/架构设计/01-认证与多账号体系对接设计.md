# 01-认证与多账号体系对接设计

---

## 1. 策略模式 (Strategy Pattern) - 认证模块

**场景**：系统存在三套独立的账号体系和不同的登录方式（密码登录、短信验证码登录，其中教师端支持手机号或工号登录）。
**设计**：定义统一的 `LoginStrategy` 接口，不同的登录方式实现该接口。
**优势**：符合开闭原则，未来如果增加微信一键登录，只需新增一个策略实现类即可，无需修改原有逻辑。

```mermaid
classDiagram
    class LoginStrategy {
        <<interface>>
        +login(LoginRequest req) LoginResult
    }
    
    class InternalUserPasswordStrategy {
        +login(LoginRequest req) LoginResult
        +resetPassword(String userId, String newPassword)
        -validatePasswordComplexity(String password) boolean
    }
    
    class TeacherPasswordStrategy {
        +login(LoginRequest req) LoginResult
        +resetPassword(String userId, String newPassword)
        -findByPhoneOrEmpNo(String identifier) User
        -validatePasswordComplexity(String password) boolean
    }
    
    class StudentSmsStrategy {
        +login(LoginRequest req) LoginResult
    }
    
    class AuthContext {
        -LoginStrategy strategy
        +executeLogin(LoginRequest req)
    }

    LoginStrategy <|.. InternalUserPasswordStrategy
    LoginStrategy <|.. TeacherPasswordStrategy
    LoginStrategy <|.. StudentSmsStrategy
    AuthContext o-- LoginStrategy
```

## 2. 安全框架与多账号体系对接设计

由于 ChordSked 存在三套完全独立的账号体系（教务端、教师端、学员端），且仅教务端需要复杂的 RBAC 角色权限控制，传统的单表用户设计（如标准 Spring Security）难以直接适配。因此，系统在对接安全框架时，采用**“统一网关鉴权 + 业务端独立提供权限数据”**的设计思想。

**框架选型建议**：使用 **Spring Security 结合 JWT**。

### 2.1 核心对接思想

1. **统一 Token 载荷设计**：JWT 中必须包含 `UserType`（标识是教务、教师还是学员）和 `UserId`。
2. **多 Realm / 多 UserDetailsService 策略**：安全框架不再直接绑定单张 User 表，而是通过 `UserType` 动态路由到不同的服务加载用户信息。
3. **权限加载策略**：
   - 教务端 (`ADMIN`): 根据 `UserId` 查 `sys_internal_user`，并关联查询 `sys_role` 和 `sys_permission`，动态加载完整的 GrantedAuthority 列表。这是唯一经过角色配置流程的账号体系。
   - 教师端 (`TEACHER`): 根据 `UserId` 查 `sys_teacher_user`，硬编码赋予一个特殊的内置标识（如 `ROLE_TEACHER`），不需要细粒度权限点，**不经过**角色配置流程。
   - 学员端 (`STUDENT`): 根据 `UserId` 查 `sys_student_user`，硬编码赋予内置标识（如 `ROLE_STUDENT`），**不经过**角色配置流程。

### 2.2 缓存一致性策略 (Redis)

在多实例部署下，用户认证状态及权限信息依赖 Redis 缓存，必须保证缓存与数据库的一致性：
1. **Token 生命周期**：登录时生成 JWT Token 并在 Redis 中记录会话状态，设置绝对过期时间（如 2 小时）。
2. **主动失效策略**：当教务端管理员在后台修改了某用户的权限（如变更角色）或禁用了某用户账号时，系统必须**主动删除或刷新**该用户在 Redis 中的权限缓存和 Token 会话状态，强制其重新拉取最新权限或下线。
3. **缓存击穿防护**：针对权限查询，如果 Redis 未命中，数据库查询时需做防击穿处理（如缓存空值并设置短过期时间）。

## 3. 核心交互时序图

### 3.1 多端统一登录与 Token 签发流程

```mermaid
sequenceDiagram
    actor Client as 客户端 (教务/教师/学员)
    participant AuthController as 认证接口层
    participant AuthStrategyFactory as 策略工厂
    participant Strategy as 具体登录策略
    participant DB as 数据库
    participant Redis as Redis缓存

    Client->>AuthController: 1. 发起登录请求 (带登录类型标识)
    AuthController->>AuthStrategyFactory: 2. 获取对应的登录策略
    AuthStrategyFactory-->>AuthController: 3. 返回 Strategy 实例
    AuthController->>Strategy: 4. 执行 login() 逻辑
    
    alt 教务/教师 (密码登录)
        Strategy->>DB: 5a. 查询用户信息及密码哈希
        DB-->>Strategy: 6a. 返回数据
        Strategy->>Strategy: 7a. 校验密码是否匹配
    else 学员 (验证码登录)
        Strategy->>Redis: 5b. 校验短信验证码
        Redis-->>Strategy: 6b. 验证码通过
        Strategy->>DB: 7b. 查询学员信息 (仅验证，不自动创建)
        alt 手机号不存在
            Strategy-->>AuthController: 7c. 抛出异常 (账号不存在)
            AuthController-->>Client: 7d. 返回 401 拒绝登录
        end
    end
    
    Strategy->>Strategy: 8. 检查账号状态 (是否锁定、禁用)
    Strategy->>Strategy: 9. 生成 JWT Token & Refresh Token
    Strategy->>Redis: 10. 缓存 Token 及用户信息
    Strategy-->>AuthController: 11. 返回 LoginResult
    AuthController-->>Client: 12. 返回 Token 及基本用户信息
```

### 3.2 Refresh Token 无感刷新机制

为了兼顾安全性和用户体验，系统采用双 Token 机制。当 Access Token 过期时，客户端可使用 Refresh Token 换取新的 Token 对。

```mermaid
sequenceDiagram
    participant Client as 客户端
    participant Interceptor as JwtAuthInterceptor
    participant AuthController as 认证接口层
    participant Redis as Redis缓存

    Client->>Interceptor: 1. 发起业务 API 请求 (携带过期的 Access Token)
    Interceptor->>Interceptor: 2. 验证发现 Access Token 已过期
    Interceptor-->>Client: 3. 返回 401 Token Expired 状态码
    
    Client->>AuthController: 4. 自动发起 /auth/refresh 请求 (携带 Refresh Token)
    AuthController->>Redis: 5. 校验 Refresh Token 是否存在且有效
    
    alt Refresh Token 有效
        AuthController->>AuthController: 6a. 生成新的 Access Token 和 Refresh Token
        AuthController->>Redis: 7a. 更新 Redis 中的 Token 缓存
        AuthController-->>Client: 8a. 返回新的 Token 对
        Client->>Client: 9a. 更新本地存储的 Token
        Client->>Interceptor: 10a. 携带新 Access Token 重新发起第1步的业务请求
    else Refresh Token 无效或过期
        AuthController-->>Client: 6b. 返回 401 (Refresh Token Invalid)
        Client->>Client: 7b. 清除本地登录状态，跳转到登录页强制重新登录
    end
```
